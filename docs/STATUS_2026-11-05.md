# Rust Radio — documentation and development status (2026-11-05)

## Scope and evidence
This document reconciles the documented standalone Rust radio implementation with outstanding acceptance work. It is a documentation checkpoint, **not** a claim that a new test suite or live hardware validation was run on 2026-11-05. The source of implementation claims is the repository README and existing GUI integration notes. Revalidate against current code and CI before marking gates complete.

## Architecture
- Portable receive-only Rust radio subsystem, independently runnable and embeddable in Rust-Boy/Pip-Boy.
- Shared native core/audio path; CLI and 480×320 egui GUI are operator frontends. The host owns HUD navigation, preferences and platform audio-device management.
- IP MP3/AAC playback and bounded M3U/PLS/redirect resolution; HLS is not supported.
- Optional direct nRSP-ST native control and audio, SDRconnect bridge, and SoapySDR USB mono-FM receive. Optional hardware paths must not become default build dependencies.
- No RF transmit, browser playback, autoplay or external player launching.

## Operator priorities — next development pass
1. **Skylab isolation:** record exact catalog URL, HTTP status/redirect chain, content type, playlist resolution, codec evidence, decode result and playback state. Run `cargo run -p rust-radio-cli -- validate skylab` and compare against `listen skylab` and GUI PLAY. Never classify a reachable website as a working audio stream. Do not change publisher endpoints without source/rights review.
2. **Catalog integrity:** validate the curated station inventory with `validate-all --json --history PATH`; distinguish catalog size from successfully decoded stations. Preserve bounded retries and DNS/private-address safeguards. Investigate stale URLs, playlist formats and codec support; do not silently introduce HLS support.
3. **Mac audio acceptance:** verify explicit Play/Stop, mute/volume, output switching after cleanup, station switching, reconnection, loss/recovery, and no overlapping playback.
4. **GUI acceptance:** check the 480×320 viewport for clipped controls, long errors, keyboard navigation and stop responsiveness. Keep diagnostic detail in setup, not on the listening surface.
5. **Receiver acceptance:** independently test direct nRSP-ST, SDRconnect and SoapySDR paths only with supported physical hardware; record device, OS, feature flags and logs.
6. **Pi 5 integration:** validate runtime native audio, resource cleanup, UI/HUD control boundaries and the pinned Rust-Boy dependency before production claims.

## Verification commands
```sh
cargo fmt --all -- --check
cargo test --workspace
cargo clippy --workspace --all-targets -- -D warnings
cargo run -p rust-radio-cli -- validate skylab
cargo run -p rust-radio-cli -- listen skylab --seconds 30
cargo run -p rust-radio-gui --bin rust-radio-gui
```
Optional feature builds must be tested separately on environments with their SDKs. Validation is silent; `listen` and GUI PLAY are intentional audio operations.

## Acceptance record template
For each check capture: UTC timestamp; commit SHA; OS/architecture; feature flags; device/output; source/station ID; resolved audio endpoint (redact secrets); stage reached (DNS/TLS/HTTP/playlist/decode/callback/audible); elapsed time; pass/fail; log or reproducible command; unresolved blocker. **Decoded PCM at callback** and **operator-confirmed audible audio** are separate assertions.
